**Who this is for:** anyone writing or debugging a client, or checking
whether a given REAPI feature is available. **What you'll have at the end:**
the complete service list with implementation status. **Time:** use as a
lookup.

NativeLink implements the [Remote Execution API](https://github.com/bazelbuild/remote-apis)
plus the adjacent protocols it depends on (ByteStream, long-running
Operations, Remote Asset and the Build Event Protocol), and defines exactly
one service of its own. Every vendored `.proto` under `nativelink-proto/` is
copied from upstream with only its licence header replaced; there are no
NativeLink-specific fields or extensions on the standard messages.

## Services [#services]

| Service | Origin | Status |
| --- | --- | --- |
| `Execution` | REAPI | Implemented |
| `ActionCache` | REAPI | Implemented |
| `ContentAddressableStorage` | REAPI | Implemented |
| `Capabilities` | REAPI | Implemented |
| `google.bytestream.ByteStream` | Google API | Implemented |
| `google.longrunning.Operations` | Google API | Partially implemented, see below |
| Remote Asset `Fetch` | Remote Asset v1 | Implemented |
| Remote Asset `Push` | Remote Asset v1 | Implemented |
| `PublishBuildEvent` | Build Event Protocol | Implemented, marked experimental |
| `WorkerApi` | **NativeLink** | Implemented |

Each is registered only if the configuration asks for it. Registration order
at startup is fixed: action cache, CAS, execution, `Operations`, fetch, push,
ByteStream, capabilities, worker API, BEP.

<Callout type="info" title="Two endpoints are not gRPC">
  The health endpoint (`/status` by default) and the admin endpoint (`/admin`
  by default; both paths are configurable) are plain HTTP handlers on the same
  listener. They will not appear in gRPC reflection, and a health check does
  not need a gRPC client.
</Callout>

## `WorkerApi`: the only NativeLink-defined service [#worker-api]

Defined in
<SourceLink file="nativelink-proto/com/github/trace_machina/nativelink/remote_execution/worker_api.proto" />.
It has **exactly one RPC**:

```proto
rpc ConnectWorker(stream UpdateForScheduler) returns (stream UpdateForWorker);
```

One bidirectional stream carries a worker's entire relationship with its
scheduler: registration, heartbeats, action assignment, progress and
completion. No polling RPC and no second connection exist. See
[worker execution](/explanations/worker-execution#the-connection-is-one-stream).

`events.proto` in the same tree declares message types only, **no services**.

## Partially implemented RPCs [#partially-implemented-rpcs]

Three `Operations` RPCs are registered and return `unimplemented`:

| RPC | Status |
| --- | --- |
| `GetOperation` | Implemented |
| `WaitOperation` | Implemented |
| `ListOperations` | `unimplemented` |
| `DeleteOperation` | `unimplemented` |
| `CancelOperation` | `unimplemented` |

A client that relies on cancellation to release cluster resources will not
get it here. Actions are instead reaped by timeout; see
[`client_action_timeout_s`](/explanations/scheduler-internals#two-timeouts-with-very-different-defaults),
which kills an action nobody is listening to.

<Callout type="info" title="SplitBlob and SpliceBlob are upstream RPCs">
  Both appear in NativeLink's vendored CAS proto and are sometimes mistaken
  for NativeLink inventions. They are part of the upstream REAPI definition
  (content-defined chunking), vendored along with everything else. NativeLink
  serves them only for CAS instances that configure `experimental_chunking`
  (or proxy to a `grpc` store that does); elsewhere the capabilities response
  reports them unsupported and the RPCs return `Unimplemented`.
  <SourceLink file="nativelink-service/src/cas_server.rs" symbol="split_blob" />
</Callout>

## What `Capabilities` advertises [#what-capabilities-advertises]

| Field | Value |
| --- | --- |
| Supported API versions | 2.0.0 to 2.3.0 |
| Digest functions | `SHA256`, `BLAKE3` |
| `max_batch_total_size_bytes` | 65536 (64 KiB) |
| `max_cas_blob_size_bytes` | 0 (no limit advertised) |
| `symlink_absolute_path_strategy` | `DISALLOWED` |
| `update_enabled` (action cache) | `true` |
| `supported_compressors` | `ZSTD` when the instance's `capabilities` entry sets `remote_cache_compression: true`; empty otherwise |
| `split_blob_support`, `splice_blob_support`, `fast_cdc_2020_params` | set when the instance's `cas` entry configures `experimental_chunking`; otherwise `false`/unset |
| `execution_capabilities` | present only when the instance's `capabilities` entry has `remote_execution`; then `exec_enabled` is `true` and the priority range is 0 to `i32::MAX` |

<SourceLink file="nativelink-service/src/capabilities_server.rs" symbol="get_capabilities" />

Two of these need a caveat.

**`exec_enabled` is hardcoded to `true`**, with a TODO in the source
acknowledging it. Whenever a `capabilities` entry names a `remote_execution`
scheduler, execution is advertised as enabled; there is no way to advertise
`exec_enabled: false`. A cache-only `capabilities` entry (no
`remote_execution`) omits `execution_capabilities` altogether, which is the
correct signal for a cache-only deployment.

**The 64 KiB batch limit is advisory and small** relative to what some
clients assume. The CAS handlers do not enforce it themselves; the hard stop
is the listener's `max_decoding_message_size` (4 MiB unless configured), and
a batch request above that is rejected at the gRPC layer. Clients that honour
the advertised limit send anything larger through ByteStream.

## Wire-level details worth knowing [#wire-level-details-worth-knowing]

**ByteStream resource names are parsed right to left.** A resource name is
`{instance_name}/blobs/{hash}/{size}`, and the instance name may itself
contain slashes, so left-to-right parsing cannot find the boundary, while
right-to-left can, because the trailing components are fixed. See
<SourceLink file="nativelink-util/src/resource_info.rs" symbol="ResourceInfo" />.

**`GetTree` page tokens are `"{hash}-{size}"`**, constructed and parsed by
splitting on `-`. They are neither opaque nor signed. The protocol asks
clients to treat them as opaque, and clients that do will keep working if the
format changes.

**The `Execute` pre-flight input check is shallow and racy by design.** It
does not walk the full input tree, and a blob can be evicted between the
check and the worker's fetch. It exists to turn the common "inputs were never
uploaded" mistake into a fast error, not to provide a guarantee. See
<SourceLink file="nativelink-service/src/execution_server.rs" symbol="ExecutionServer" />.

**`ActionStage::CacheCheck` is never emitted.** The cache lookup happens in a
decorator in front of the scheduler, so the state is skipped entirely. A
client waiting to observe it will wait forever.

**Final action failure arrives as success.** An action that exhausts its
retries returns `ActionStage::Completed` with `ActionResult.error` set: a
successful RPC describing a failed action. This is what the REAPI specifies.
Clients that only inspect the gRPC status will misread it.

**`server_logs` is never populated.** The field exists; the worker does not
fill it.

## Remote Asset `Fetch` behaviour [#remote-asset-fetch]

These are the behaviours of the `url` fetcher and the `cache` fetcher
behind the `Fetch` service that the Remote Asset protocol leaves to the server.

### Redirects [#fetch-redirects]

The `url` fetcher follows at most 10 redirects per URI. It refuses a redirect
from `https` to `http`, for every request, and the URI then counts as failed
(the next one is tried; if none succeeds the request reports `NOT_FOUND` with
the reason in its message). When a redirect leaves the origin the request went
to, the `Authorization`, `Cookie`, `Proxy-Authorization` and `WWW-Authenticate`
headers sent with `http_header:` qualifiers are dropped, so those credentials
are never offered to another host. Any other header you set is forwarded.

<SourceLink file="nativelink-fetch/src/url_fetcher.rs" symbol="redirect_policy" />

### Timeouts [#fetch-timeouts]

A request's `timeout` bounds the retrieval from the origin: every URI attempt,
the download, checksum verification and the CAS upload. A `cache` fetcher
clamps it to `min_timeout_s` and `max_timeout_s`, and the `url` fetcher's
`max_fetch_duration_s` (one hour by default) caps it, and bounds a request
with no timeout too. Running out reports `DEADLINE_EXCEEDED` in the response
`status`. A timeout of zero is the same as none, and a negative or
malformed one fails the call with `INVALID_ARGUMENT`.

The timeout does not bound the RPC. When the RPC deadline comes first the call
fails with a `DEADLINE_EXCEEDED` RPC error, and a fetch run by a `cache`
fetcher carries on; retrying the same pinned request joins it. Nor does it count
time spent waiting for one of the `cache` fetcher's
`max_concurrent_fetches` slots, which retrieves nothing: only the RPC deadline
bounds that wait, and a client that goes away while waiting leaves no work
behind.

A pinned request, one that carries a checksum, is fetched one URI at a time,
in order, and concurrent pinned requests share the download of each URI they
have in common, even when they list different mirrors. A URI that fails on its
own (not found, unreachable, refused, a checksum mismatch, too large) moves on
to the next; a failure the other URIs would share, such as a bad request, ends
the request. An unpinned request always runs its own fetch: it accepts only what the origin
serves now, and Bazel sets `oldest_content_accepted` to the time of the request,
so joining a fetch that started earlier could hand it older content. Requests
that send different `http_header:` or `http_header_url:` qualifiers for a URI
do not share its download: different credentials can get different answers from the origin, so
each runs its own fetch. A shared fetch runs until the latest of its requests'
timeouts, each counted from when its request arrived at the running fetch, so a
request with a short timeout does not cut the fetch short for one with a longer
timeout. Each request still gets `DEADLINE_EXCEEDED` once its own timeout has
passed with the download under way. Time an `action_verify` fetcher spends
running its action is not counted.

<SourceLink file="nativelink-fetch/src/fetcher.rs" symbol="SharedDeadline" />

### How long a fetched asset stays cached [#fetch-freshness]

What a fetch stores is the asset's URI and qualifiers mapped to a digest, and
how long that mapping is served depends on whether the request is *pinned*. A
request is pinned when it carries a checksum: `checksum.sri`, a hex
`checksum.sha*`, `checksum.action_digest`, or a tree checksum such as
`checksum.nar`, `checksum.git_tree` or `checksum.h1`. The server decides this
from the checksums parsed off the request, not from a list of qualifier names,
so a newly supported checksum is covered without a change here.

- **A pinned entry never expires.** The content has to match the checksum, so it
  cannot legitimately change, and the origin's caching headers are ignored.
  Nor does it depend on the URI: a pinned entry is keyed on the qualifiers
  alone, so a request that lists other mirrors, or the same ones in another
  order, finds what an earlier `Fetch` or `Push` stored. Any other qualifier
  still counts, including `bazel.canonical_id`.
- **An unpinned entry expires.** Without a checksum the first answer for a URL
  would otherwise be served forever. The `url` fetcher reads the freshness of
  the *final* response, after any redirects, as a shared cache would (RFC 9111):
  `Cache-Control: s-maxage`, else `max-age`, else `Expires` less `Date`, less
  `Age`. `no-store`, `no-cache` and `private` make the entry stale at once, and
  so does `max-age=0` or an `Expires` that is not a valid date. Heuristic
  freshness is not used: a response with no such header gets the configured
  default. The result is limited to between `unpinned_min_ttl_s` and
  `unpinned_max_ttl_s` (a response that must not be reused is not raised to the
  minimum), and the entry is written with that expiry, which `Fetch` reports in
  `expires_at`. A stale entry is a miss: the next request goes back
  to the origin.

The three fields are on the
[`cache` fetcher](/reference/nativelink-config/main#cachespec),
defaulting to one day, five minutes and 30 days. A client can always ask for
newer content than an entry holds with `oldest_content_accepted`.

### Checking a stale entry with the origin [#fetch-revalidation]

When an unpinned entry is stale and the origin gave it an `ETag` or a
`Last-Modified` (the `url` fetcher stores both with the entry), the `Fetch`
service does not download the content again. It passes the stale entry
down the fetcher chain, and the `url` fetcher sends the request with
`If-None-Match` and `If-Modified-Since`:

- **`304 Not Modified`**: nothing is downloaded. The fetcher checks that the
  stored blob, or for a directory the whole tree and every file in it, is still
  in the CAS, and if so answers with the old digest. The `cache`
  fetcher stores the entry again with a new `stored_at` and an `expire_at`
  taken from the `304`'s own caching headers, so it is fresh again. If the
  content has left the CAS the request is repeated without the conditional headers
  and downloaded in full.
- **`200`**: the new content goes through the usual path, checksum-free like any
  unpinned request, and replaces the entry.

An entry is checked this way whether it expired or the client's
`oldest_content_accepted` rules it out: an origin that confirms nothing has
changed has shown the content is current as of now, which is as new as anything
it could serve. A pinned request is never checked this way, and an entry with neither
`ETag` nor `Last-Modified` (one that was pushed, or whose origin sent neither
header) is downloaded again as before.

The stale entry travels on the fetch job as a request parameter, outside its
identity. Only unpinned requests carry one, and those never share an in-flight
fetch, so each fetch checks its own request's entry.

## Remote Asset `Push` references [#remote-asset-push-references]

`PushBlob` and `PushDirectory` keep the `references_blobs` and
`references_directories` they are given with the entry they write. They are
never returned, but a `completeness_checking` fetch store checks them like the
asset itself: every referenced blob, and every `Directory` and file of each
referenced tree, has to be in the CAS. Once any of them is evicted, a `Fetch`
for the asset misses instead of returning content whose references are gone,
such as a BuildStream artifact whose file trees have left the CAS. A malformed
referenced digest fails the push with `INVALID_ARGUMENT`.
